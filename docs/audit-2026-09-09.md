# Code audit, 2026-09-09

This review covered secret persistence, bootstrap authentication, initial owner setup, passkey step-up, and key rotation. It was a source review with focused regression tests, not a penetration test.

## Fixed

- P1: Concurrent writes could store ciphertext authenticated for a different secret id or version. `apps/control-plane/src/server/vault/secrets.ts` reads the existing record before encryption, while `packages/vault-store/src/repositories/secrets.ts` previously incremented the stored version without checking that read. Writes now require the expected version and matching id in the SQL statement. A stale writer fails without replacing the winning ciphertext. The service regression runs concurrent creation and replacement and decrypts the surviving value.
- P2: An unreadable CIDR policy fell back to `::1/128`, which admitted loopback despite the intended fail-closed behavior. `apps/control-plane/src/server/vault/bootstrap-auth.ts` now rejects an unreadable policy directly. A regression submits loopback against malformed policy JSON.
- The dotenv import comment now describes its actual guarantee. Parsing and validation finish before writes, but a later database or concurrent-write failure can leave earlier entries applied.
- P1: Setup sessions received passkey step-up authority before an assertion. The auth session hook now stamps `stepUpAt` only when Better Auth creates a session in `/passkey/verify-authentication`. Setup and registration sessions receive no timestamp. Tests cover setup, registration, missing context, and successful authentication. The installed Better Auth 1.7.2 passkey implementation creates the authentication session only after verifying the assertion.

## Follow-up findings

### P1: Environment rotation can race a secret write

`apps/control-plane/src/server/vault/rotation.ts` snapshots secrets before encryption, then `packages/vault-store/src/repositories/secrets.ts` builds unconditional rotation updates by id. If a regular write commits after the snapshot, rotation can replace its ciphertext with bytes authenticated for an older secret version while preserving the newer database version. Decryption then fails. A newly created secret can also miss the rotation snapshot and remain encrypted with the retired key.

Serialize writes, imports, and rotations for an environment through the same authority, or implement a transaction that rejects the entire rotation when its secret snapshot or active key changes. Guarding only the normal write version does not solve this race. Project-key rotation likewise needs coordination with environment creation and key rotation.

### P2: Initial-owner creation is not atomic

`apps/control-plane/src/server/auth/setup-plugin.ts` checks `listUsers(1)` before calling `createUser`. Two requests with a valid setup token and different emails can both observe an empty user table and create separate owners. The auth schema has no constraint enforcing a single setup claim.

Make the initial claim and owner creation atomic in the auth database, with a retry or recovery path if session issuance fails afterward. A process-local mutex would not cover separate Worker instances.
